Recipes

Add an item, add a tab, connect the real API, swap the map boundaries.

Step-by-step instructions for the changes you are most likely to make. Each one names the exact files to touch.

Add a new reporting item

Example: a card on the Services tab showing credentials added per day. The numbers already exist in daily-metrics.json (the credentialsAdded field), so this needs a view and an item.

  1. Decide the view's name and shape. Call it vw_CredentialsAddedDaily, returning { dates: string[], added: number[] }. Writing the shape down first is the important part: it is the contract the real API will have to meet.
  2. Add the view to the mock source. In js/data/mock-source.mjs, inside the views object, next to vw_CredentialChecksDaily: series(field, platform) gives the daily values for a field, and win(list, range) keeps the last range days. credentialsAdded is already in the FIELDS list at the top of the file; a brand-new field would need adding there too.
  3. Add the item. In js/items/services.mjs, add an object to the list. Pick the next unused id (check the item catalog). lineChart, fmt and sum are already imported at the top of that file. If you use a helper that isn't, add it to the import line.
  4. Place it. In js/items/index.mjs, add ['ITM-47', 's6'] to a section in LAYOUT, for example the Digital credentials section under services. Keep each row adding up to 12: here it pairs with another s6 card, or use s12 for a full row.
  5. Refresh and check. The card appears in that section. Check that it changes with the period and phone-type filters, that How it's built opens, and that it looks right at phone width and in dark theme.
  6. Write it down. Add a row for the view to VIEWS in docs/items.mjs (so the catalog shows its shape and file) and to the data contract table in README.md.
If the card shows "Couldn't load vw_…"

The view name in the item does not match a key in views, or the view threw an error. Open the browser console (F12) for the message.

Common extras

  • Events on the chart: add also: { events: 'vw_Events' } to the item, make the signature render(h, d, s, ctx, more), and pass events: more.events.filter(e => e.inPeriod === 'current') to lineChart.
  • A target: add a row to targets.json, add also: { targets: 'vw_Targets' }, and use findTarget and evaluate from js/ui/status.mjs. To put it on the scorecard, also add the measure to vw_Scorecard.
  • A control in the card: add a key to js/state.mjs, then control, deps and params on the item. See controls.
  • On a slide: add ['ITM-47', 's6'] to a slide in STORY in js/items/index.mjs, then check the slide still fits without scrolling.
  • New mock numbers: put them in a JSON file in data/mock/, load it in the Promise.all at the top of createMockSource, and read it in your view.

Add a tab

  1. Create the file js/items/payments.mjs that exports a list of items, each with tab: 'payments':
  2. Register it in js/items/index.mjs: import the file, add a tab, and add the items to ITEMS.
  3. Lay it out. In the same file, add the tab to LAYOUT with at least one section:
  4. That's all. main.mjs builds the tab link, the panel, a heading for each section after the first, and the cards from these lists. The tab's address is #payments. Use a short lower-case id with no spaces.

For text under a tab's cards (like the privacy note on Location), add an entry to TAB_FOOTERS in the same file.

Move a card or reorganise a tab

Everything about placement lives in LAYOUT in js/items/index.mjs. No item file needs to change.

  1. Move a card: cut its ['ITM-xx', 's6'] pair from one section and paste it into another, on the same tab or a different one.
  2. Change its width: change the span. Rows are 12 columns, so two s6, an s8 with an s4, or one s12. A row that adds up to less than 12 leaves a gap.
  3. Add, rename or reorder a section: edit the section objects in the tab's list. The first section of a tab sits on the cover band and its title is not shown.
  4. Refresh and check the tab at desktop and phone width, and in Present mode if the card is on a slide (slides are listed separately in STORY).

Switch a feature off (or back on)

js/config.mjs has a features list. Fuel exemption is switched off for now:

  • Items with feature: 'fuelExemption' are left out of ITEMS, so they disappear from every tab, slide, the Wanted list and the item catalog.
  • Service selectors drop the matching option, and the mock source drops the fuel transaction type and the Fuel exemption portal backend, rescaling the other services' shares so totals still add up.
  • Code, mock data and the Fuel exemption section in LAYOUT stay in place. Set the switch to true and refresh to bring it all back.
  • To make another feature switchable, add a key to features, tag its items with feature: 'key', and filter any options or data rows with featureOn('key').

Connect the real API

The dashboard never talks to a database. It asks an API for each view by name, and the API returns JSON in the agreed shape.

  1. Build the views in Fabric. One SQL view (or function) per item. The How it's built panel on each card has a starting query and the view's name.
  2. Put an API in front of them. Either Fabric's API for GraphQL behind a gateway, or a small backend such as an Azure Function. It must return aggregates only, and it is where sign-in is enforced. The browser must never hold database credentials.
  3. Match the request. For each item the dashboard sends: from is the first day; to is the day after the last day; platform is left out for "All". Items add their own parameters, for example txType, lga or threshold.
  4. Match the response. Return exactly the shape in the item catalog (the README has the full table). The fastest check: open the mock dashboard, and in the console compare against what the mock returns.
  5. Switch the source. In js/config.mjs: While testing you can leave the default and add ?source=api to the address instead.
  6. Move one view at a time. A view the API doesn't have yet shows a short error in its card; the rest of the dashboard keeps working. Location needs the most care: match coordinates to councils inside Fabric and return council-level counts only, leaving out councils under the threshold.
Using GraphQL instead of one address per view?

Keep the interface and change only query() in js/data/api-source.mjs to send a GraphQL query per view and reshape the answer. Nothing else needs to know.

Swap in the full ABS boundary file

The map's boundary file is heavily simplified to keep it small, so small inner-Adelaide councils look angular. For production, build a better one from the ABS download. The commands below were written from the ABS field names and have not been run here, so check the names against your download.

  1. Download "Local Government Areas – 2023 – Shapefile" from the ABS digital boundary files page (ASGS Edition 3) and unzip it.
  2. Install mapshaper, a free tool for map files: npm install -g mapshaper.
  3. Filter, simplify and convert: Raise the percentage until inner Adelaide looks right; 4 to 8% is usually under 400 KB.
  4. Add the dashboard's council codes. Each feature needs a code property matching data/reference/lga.json (for example ADE). Match on absCode, which is in both files, with a few lines of Node or mapshaper's -join.
  5. Refresh. No code changes are needed. Label positions, the enlarged Adelaide panel and keyboard order are all worked out from the shapes. The layer must be named lga.
  6. Keep the attribution. The line under the map credits the ABS under CC BY 4.0. If you no longer simplify, change its wording in js/ui/geomap.mjs.

Put it somewhere others can see

It is a static site, so any static host works. Azure Static Web Apps fits the Azure and Fabric stack and supports Microsoft Entra ID sign-in; staticwebapp.config.json is already in the folder. Keep any copy with real data behind organisational sign-in.
